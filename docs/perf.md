run in Chromium with the extension loaded, minus the same scenario without it.
Absolute numbers from a container mean nothing; a difference measured back to
back does. Firefox will differ in magnitude, not in shape.

## What profiling changed

Two things showed up only under measurement, and both are now fixed:

- **Rule resolution was on the hot path.** `resolveSpeed` parses every stored
  pattern, and the enforcer asks for the target on every media event. With two
  hundred rules that measured at ~0.3 ms per call, so the answer is now cached in
  the controller until the settings or the frame's URL change.
- **The mutation observer asked every added node a question it could not answer.**
  A page that appends ten thousand leaf nodes hands the observer ten thousand
  added nodes; running a selector query on each cost more than everything else
  combined. The O(1) questions — is this media, does it have a shadow root, does
  it have any element children at all — are now asked first, and the load figure
  above dropped from ~45 ms to ~29 ms.

The shadow-host crawl, which is the only walk over every element on the page,
was also moved off the critical path onto an idle callback. It does not change
the totals above, because those measure total script time rather than blocking
time — but it is the difference between the work happening while the page is
trying to render and after it has.

## Micro-benchmarks

`npm run bench` measures the pure functions directly. The figures that matter:

| Operation | Rate |
| --- | --- |
| Compare a rate to the target | ~10.9 M/s |
| Match one parsed pattern against one parsed URL | ~5.9 M/s |
| Resolve a speed with no rules | ~1.3 M/s |
| Resolve a speed with a handful of rules | ~300 K/s |
| Resolve a speed with 200 rules | ~3.5 K/s (which is why it is cached) |
